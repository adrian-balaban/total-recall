## 🚀 Install / setup

`install.sh` (plugin root) is the one-shot, state-aware setup script: profile prompt (a. minimal — no optional deps / b. complete — hybrid vector search, the DEFAULT; embeddings come from a local in-process HuggingFace MiniLM — no external service or daemon) → vault dirs (incl. one-time local-only `git init` of the personal vault for H1 durability) → MCP registration → index build → optional org vault / vector search → verify. Hooks are NOT wired by install.sh — they auto-load from the plugin manifest's `hooks/hooks.json`; a manual clone gets the same via `claude plugin install "$(pwd)"`. Run `./install.sh --help` for flags (`-y`/`--yes`, `--default`/`--complete`/`--vector` (alias group), `--no-vector`, `--statusline`, `--gemini` (requires `agy` CLI), `--org-repo`, `--allowed-email-domain`, `--plugin-root`, `-h`/`--help`). User-facing install docs live in `INSTALL.md` (incl. Windows/Git Bash notes) — keep it in sync with install.sh flags. (The `--standalone` user-scope hook-wiring path was removed — there is now exactly one hook source, `hooks/hooks.json`, so no inline copy to keep in sync.)

## 📦 Build artifacts (`dist/`)

`dist/` is **gitignored — never commit it.** It is produced by GitHub Actions and by nothing else in the normal flow.

How the pieces fit:

- `.github/workflows/mutation.yml` is the gate: `npm ci` → `npm audit --audit-level=critical --omit=dev` → `npm run typecheck` → `npm run build` (proving the bundle builds, and that `sync:version` leaves the manifests unchanged) → `npm test` (the **full** unit suite) → `npm run test:integration` (boots the real bundle over stdio) → Stryker ≥65%. **The build must stay ahead of the tests**: `dist/` is gitignored, and `hooks/scripts/store-learning.mjs` imports `dist/frontmatter.mjs` at runtime, so `hook-scripts.test.ts` fails with ERR_MODULE_NOT_FOUND on an unbuilt tree. It runs on every push/PR to `main`. The explicit `npm test` matters: Stryker's dry run only executes the ~21-file allow-list in `vitest.stryker.config.ts` (293 of 744 tests), so without it most of the suite would run nowhere now that the local pre-commit gate is gone.
- `.github/workflows/release.yml` runs after a green gate, rebuilds `dist/`, and force-pushes `main`'s validated tree **plus** the built `dist/` to the **`release` branch**. It also cuts a `vX.Y.Z` tag + notes when `package.json`'s version has advanced.
- `.claude-plugin/marketplace.json` pins its `git-subdir` source to `"ref": "release"`, so what consumers install is always a GitHub-built bundle. `main` stays artifact-free.

Consequences worth internalising:

- **Do not `git add -f` `dist/`.** The only writer is CI. A hand-published bundle is unreviewable and defeats the gate.
- **A change is not live for consumers until the release workflow refreshes `release`.** Pushing to `main` alone changes nothing for anyone installing from the marketplace — the gate has to go green first. That is the intended trade: slower propagation, no unverified bundle.
- **Locally you still run `npm run build`** to get a runnable `dist/index.js` (the MCP server, `hooks/scripts/store-learning.mjs`'s import of `dist/frontmatter.mjs`, and `npm run test:integration` all need it). That is a dev convenience, not a release step, and its output is ignored by git.
- `install.sh` builds `dist/` itself when it is missing (`npm ci && npm run build`), so a manual clone of `main` still installs. It detects the plugin root by `.claude-plugin/plugin.json` — a tracked file — rather than by `dist/index.js`, which no longer exists in a fresh checkout.

## ✅ Before committing

There is **no local build pipeline** — the former `npm run release:build` / `scripts/release-build.sh` gate was removed in v1.1.19. Verification is GitHub Actions only.

The one step CI cannot do for you:

**Increase the version.** Bump it in **`package.json` only** — it is the single source of truth. Do **not** hand-edit `.claude-plugin/plugin.json` or `gemini-extension.json`: `npm run build` runs `sync:version` (`scripts/sync-version.mjs`), which copies `package.json`'s version into both, and CI fails if they are out of sync. `claude plugin update` only picks up the change when the version advances, so a fix committed at the same version is invisible to consumers. Use patch (`1.0.4 → 1.0.5`) for fixes, minor for new tools/features. The build injects the version into the bundle via `--define:__PLUGIN_VERSION__` (from `$npm_package_version`).

Then `git add -A && git commit -S` from the plugin root (signed commit), and push.

Running `npm test` and `npm run typecheck` locally before pushing is optional now, not mandated — CI runs both. When you do run them locally, run with a **clean `HOME`** (`HOME=$(mktemp -d) npm test`): a developer box carries `~/.total-recall/config.json`, and env-dependent tests can pass there while failing on a fresh CI runner. That is exactly how the `sync-org-memory.mjs` import-time `process.exit(1)` survived until v1.1.21. A red gate means the `release` branch simply does not refresh, so consumers keep the last good build rather than receiving a broken one. That is the safety property untracking `dist/` bought. The flip side: a red gate is also **silent** from a consumer's perspective — nothing breaks, but nothing ships either, so check the run after pushing a fix you expect people to receive.

### Git Commit & Tag Signing Policy

Because plugin distribution uses `git-subdir` (where `claude plugin install` and `claude plugin update` fetch directly from this repository's git commit history without an intermediary registry like npm), signed commits and tags are **strongly enforced**:

- **Configure local GPG/SSH signing:**
  ```bash
  git config --global commit.gpgsign true
  git config --global tag.gpgsign true
  ```
- **Release Tags:** Always sign release tags (e.g. `git tag -s v1.1.14 -m "Release v1.1.14"`). Note that `.github/workflows/release.yml` cuts unsigned lightweight tags automatically when `package.json`'s version changes on green CI, and publishes the built `release` branch under the `github-actions[bot]` identity; sign manually only when you tag by hand.

## 🏗️ Architecture

This is an MCP server that exposes 17 tools for persistent memory management. It runs as a stdio process compatible with Claude Code and Gemini CLI. The entry point `src/index.ts` is a thin boot stub (signal handlers + `main()`); everything else is split across focused modules:

- `src/server.ts` — `McpServer` construction, the six `register(server)` calls that wire the 17 tools, and `main()`. (6.1-6.3: migrated from the deprecated low-level `Server` + `setRequestHandler(ListTools/CallTool)` to the high-level `McpServer` + `registerTool`. server.ts no longer owns schemas or a dispatch table — each tool's Zod schema + handler + `register()` are co-located in their `tools/*.ts` module, and `registerTool`'s `safeParse` enforces the schema at the dispatch boundary.)
- `src/state.ts` — the shared in-memory singletons (`memIndex`, `invertedIndex`, `errors`, `perfSamples`). These are `const` objects with a stable identity; every module that reads/writes the index imports them from here so there is exactly one index across the process. Mutate in place (`memIndex[key] = …`, `delete memIndex[key]`); the two sites that formerly reassigned them (`loadIndexes`, `rebuildInvertedIndex`) now clear-then-populate the same object
- `src/paths.ts` — vault/DB/index paths (supports custom paths resolved from `~/.total-recall/config.json`), `EXCLUDED_DIRS`, `DEFAULT_CATEGORIES`, `ensureDir`
- `src/types.ts` — `MemoryFrontmatter`, `MemoryMetadata`, `Index`, `InvertedIndex`
- `src/lru-cache.ts` — `LRUCache` + the shared `contentCache` instance
- `src/persistence.ts` — `loadIndexes`, debounced `scheduleSave`/`scheduleIdfRecalc` (saves the incrementally updated inverted index to disk), `saveNow`/`recalcIdfNow`/`flushPending`, `buildIndexCache` (owns the debounce timers)
- `src/tfidf.ts` — `tokenize`, `rebuildInvertedIndex`, `registerDocument`/`deregisterDocument` (incremental updates), `tfidfSearch` (supports RO/EN bilingual query expansion if `enableMultilingualSearch` is true)
- `src/vault-scan.ts` — `reconcileIndex`, `indexFile`, `deriveCategory`, `keyFromPath`, `slugify`, `tokenEstimate`
- `src/dates.ts` — `parseRelativeDate`
- `src/journal.ts` — `appendJournal`
- `src/tools/{store,recall,query,mutate,rerank,bulk}.ts` — the 17 tool implementations. Each module also exports a `register(server)` (6.3) that calls `server.registerTool(name, { description, inputSchema: <Zod raw shape> }, wrapHandler(name, handler))`, co-locating each tool's Zod schema with the handler it validates
- `src/tools/registry.ts` — `wrapHandler` (6.1-6.3): the CallToolResult envelope + `recordPerfSample`/`recordError` instrumentation the old `setRequestHandler(CallTool)` owned. `registerTool` runs `safeParse` on the caller's args BEFORE the wrapped handler (6.2), so malformed calls are rejected at the dispatch boundary with a parse-error result; the handlers' defensive coercion (`String(args.title ?? '')`, scalar-tags leniency) is retained as belt-and-suspenders for the MCP path and the sole guard for the internal path (`import_memories` round-trip + unit tests, which bypass the Zod boundary)

**Data flow:**
1. On boot, loads `~/.total-recall/index.json` into `memIndex` (invertedIndex.json is NOT loaded — `main()` rebuilds the inverted index synchronously via `recalcIdfNow` right after `reconcileIndex`, so the disk copy was a dead read; `markIndexFresh` then gates the debounced recalc so the boot timer doesn't redo it). Always scans both vaults (unconditional; reconciles against disk to surface newly pulled org memories and catch missed flushes).
2. All tool calls operate against the in-memory `memIndex` (Record<key, MemoryMetadata>).
3. Writes are debounced: `scheduleSave()` waits 1s → writes index → triggers `scheduleIdfRecalc()` at +2s → writes `.index-cache.txt` and `invertedIndex.json` incrementally (no full rebuild).

**Dual vault routing:**
- Personal vault: `~/.total-recall/personal-vault/` (unless overridden in `config.json` via `personalVault`) — default for all memories
- Org vault: `~/.total-recall/org/org-vault/` (unless overridden in `config.json` via `orgVault`) — used when tag `org` is present; synced to the repo configured via `orgRepo` in `~/.total-recall/config.json` via `scripts/sync-org-memory.mjs`. The sync branch is `config.orgBranch` if set, else the current local branch, else the literal fallback `org-vault` (`BRANCH` resolution in `sync-org-memory.mjs`); `pull-org-vault.sh` reads the same `orgBranch` key so pull and push agree. (Example: this repo's `config.json` sets `orgBranch: "knowledge"`.)
- Keys are relative paths from vault root; org keys are prefixed `org/`
- Org sync runs a privacy filter: blocks secret tokens, credit cards, IBANs, formatted phone numbers, and all email addresses (fail-closed by default; allow your company domain via `allowedEmailDomains` in `~/.total-recall/config.json`) before any push. (Pronouns were intentionally removed — the false-positive rate blocked legitimate org memories; the real "personal, don't sync" guard is the mutual-exclusion of the `personal` and `org` tags. Phone numbers, credit cards, and IBANs were initially removed too — a bare phone regex tripped on any 10-digit run (unix timestamps, AWS account ids, git SHA fragments) — and were RE-ADDED in 7.3 in validated, low-FP form: Luhn checksum for CC, ISO 13616 mod-97 for IBAN, formatted-only shape for phone. The validators reject ~90% of random digit/alphanumeric runs, so the FP rate is negligible. The personal vault gets only a NON-BLOCKING stderr warning on a known-prefix secret token — the broader detectors are intentionally NOT applied there to keep its FP rate near zero; see INSTALL.md "Privacy model".) The `EMAIL_RE` host class includes non-ASCII (IDN) chars (` -`) so a personal email at an internationalized host (`user@münchen.de`, `user@пример.рф`) is blocked just like an ASCII one — never narrow the host class back to ASCII-only, or the IDN bypass reopens; the IDN cases are pinned by a regression test in `sync-org-memory.test.ts`.

**Search pipeline:**
- Primary: TF-IDF (`invertedIndex.json`) × Ebbinghaus retention decay (`src/ebbinghaus.ts`). Expanded with RO/EN translations if `enableMultilingualSearch` is true.
- TF-IDF tokenizes over `title + tags + contentPreview` (first ~500 chars of body stored in the index, not the full file); the boost path (`×2` title match, `×1.5` tag match) memoizes the lowercased title + tags per doc-key across the query-token loop, so a Q-token query matching D docs pays one `toLowerCase` per doc, not Q·D — never re-introduce a per-(token, doc) `toLowerCase` in `tfidfSearch`
- Optional hybrid: TF-IDF + vector embeddings fused via Reciprocal Rank Fusion (`src/rrf.ts`)
- Vector path uses the in-process HuggingFace pipeline (`Xenova/all-MiniLM-L6-v2`, 384-dim) as its only embedding provider. Gracefully degrades to TF-IDF on any vector-path error (embed/sqlite-vec/RRF), recording the failure to `get_stats.recentErrors` via `recordError` so a recurring vector failure is observable, not silent

**Supporting modules:**
- `src/frontmatter.ts` — minimal YAML-frontmatter parse/stringify (replaces gray-matter; formats/sorts keys consistently: title, tags, author, sessions, created, updated, importanceScore, custom)
- `src/ebbinghaus.ts` — retention strength formula: `clamp(importance × exp(-λ × days) × (1 + accessCount × 0.2 + confirmations × 0.1 − flags × 0.1), 0, 1)` (confirmations/flags come from `confirm_memory`)
- `src/embeddings.ts` — in-process HuggingFace pipeline embeddings (single provider, post-Phase-0); lazy-loaded + no-op if deps absent; a failed load is not cached so the next embed retries. Also exports `depsInstalled()` — a capability probe (can `@huggingface/transformers` + `sqlite-vec` import, and can `better-sqlite3` instantiate `new Database(':memory:')`) distinct from `isVectorAvailable()` (which only answers "has the HF pipeline lazy-loaded yet"). `get_stats` uses `depsInstalled()` so vector search defaults to **enabled** on a fresh session (before any `embed()` triggers the lazy load) instead of reporting disabled-while-idle; a `true` result is latched per-process, a `false` result re-probes (so a mid-session self-heal rebuild is reflected on the next `get_stats`). `__testSetDepsInstalled(null)` is the test seam
- `src/vectorStore.ts` — sqlite-vec upsert/search/delete wrapper
- `src/rrf.ts` — Reciprocal Rank Fusion (k=60)

**Hooks** (`hooks/hooks.json`):
- `SessionStart`: pull org vault → rebuild index cache → inject memory index → check org-sync errors (`check-sync-errors.sh` warns if pushes failed since the last success)
- `PostToolUse` (store/update/delete): sync to org vault if tagged `org`
- `PreCompact`: extract 0–3 learnings from transcript via `extract-and-store-memories.sh` (reads `transcript_path` from the hook's stdin JSON — Claude Code's common hook input, *not* an env var) → pipes JSON lines to `hooks/scripts/store-learning.mjs` which writes them directly as frontmatter `.md` files to the personal vault (no MCP round-trip; never overwrites existing files)
- `SessionEnd`: `session-end.sh` logs the session, SIGTERMs the MCP child to flush pending embedding writes, auto-commits the personal vault if it is a git repo (H1 durability; see gotcha), and emits `{"continue":true}` — NOT a `hookSpecificOutput.additionalContext` envelope (SessionEnd rejects that shape as "Invalid input", unlike SessionStart)

## 🧠 Memory Workflow

When using total-recall tools, follow the retrieval order in `skills/memory-workflow/SKILL.md`:
1. Check the injected index already in context (free)
2. `get_memories_by_keys(..., summary=true)` — if key is known
3. `get_memories_by_keys(..., summary=false)` — if full content needed
4. `search_index(query=...)` — metadata-only, no file reads
5. `recall_memory(query=..., full=false)` — TF-IDF + Ebbinghaus
6. `recall_memory(query=..., full=true)` — with full content

Every stored memory must include a `## Executive Summary` section (answers WHY it matters, not just WHAT). Call `store_memory` from the main agent, never a subagent. Check for duplicates with `search_index` before storing. Set `importanceScore` (0.3=low, 0.7=high, 1.0=critical).

## ⚠️ Key Gotchas

- `get_stats` vector reporting (v1.1.9) — `vector.enabled` / `depsPresent` / the back-compat `vectorSearchEnabled` are driven by the `depsInstalled()` capability probe (`src/embeddings.ts`), NOT the old `isVectorAvailable()` ("has the HF pipeline lazy-loaded yet"). On a fresh session the pipeline has never loaded, so the old wiring reported `depsPresent: false` and made vector search look disabled when it was merely idle — driving users to "fix" a non-problem and to miss the real footgun (a missing `better-sqlite3` binding, the post-`claude plugin update` source-only state). `depsInstalled()` probes what matters — can the three optional deps import AND can `better-sqlite3` instantiate `new Database(':memory:')` (the binding test) — with no side effects (no model load, no DB file touch). `enabled = isVectorAvailable() || depsInstalled()` → defaults to true when deps are loadable, honestly false only when the binding is truly missing. A `true` result latches per-process; a `false` re-probes so a mid-session self-heal rebuild is reflected on the next `get_stats`. Do not "simplify" back to `isVectorAvailable()` alone, or a fresh session reverts to reporting disabled-while-idle. Pinned by the `get_stats` describe block in `index.test.ts` (enabled-when-deps-present / disabled-when-absent) and the `depsInstalled probe` describe block in `embeddings.test.ts`.
- Multilingual expansion **dedupes** (v1.1.17) — `tfidfSearch`'s bilingual expansion collects tokens through a `Set` (first-seen order preserved, so the title/tag boost path still sees each distinct token once). `BILINGUAL_DICT` is bidirectional — 17 of its 28 entries map RO→EN *and* EN→RO — so without the dedupe a query holding a word **and** its translation collided (`"decizie decision"` → `['decizie','decision','decision','decizie']`) and the per-token scoring loop added a matching doc's `(1+log tf)·idf·boost` twice, ~2× its monolingual baseline. Relatedly, **never add a dict key whose value equals itself**: the removed `'concept': 'concept'` self-mapping double-counted on a plain single-word query with no mixed-language input at all. Pinned by the `dedupe prevents double-counting` block in `tfidf-multilingual.test.ts`.
- `get_memories_by_keys(summary=true)` exec-summary capture **stops at the next `## ` heading** (v1.1.17) — `query.ts` matches `/^## Executive Summary\n+([\s\S]*?)(?=\n##\s|\n*$)/m` and re-applies the 500-char cap after. The prior greedy `[\s\S]{0,500}` had no section boundary, so the common case (a short summary — `withExecutiveSummary` lays bodies out as `## Executive Summary\n\n<summary>\n\n## <next>…`) swallowed the following section up to the cap and leaked it into the SessionStart injected index, costing tokens every session. The `\n*$` arm handles an exec summary that is the last/only section; a legacy headerless body still falls back to `slice(0,500)`. Never drop the lookahead — the bleed returns silently. Pinned by the `summary=true exec-summary extraction` block in `query.test.ts`.
- Every vault-touching test file **must** hoist a `process.env.HOME` override before its imports — `paths.ts` captures `os.homedir()` exactly once at module load, so a plain assignment after the import list is too late. `embeddings.test.ts` was the last file missing one (fixed v1.1.17) and consequently read the developer's real `~/.total-recall/config.json`, making test output machine-dependent. Use the `vi.hoisted(() => { process.env.HOME = '/tmp/tr-<name>-' + process.pid; })` pattern.
- `org` tag routes to the shared vault
- `EXCLUDED_DIRS` in `src/paths.ts` skips `projects`, `templates`, `.obsidian`, etc. during vault scan
- `category` is derived from the first subdirectory under the vault root; files at vault root get category `knowledge`
- `slugify` (vault-scan.ts) collapses an empty or all-punctuation title to `''`, then falls back to the literal slug `'untitled'` (`slug || 'untitled'`) — without it an empty title would produce `knowledge/.md` with the path-shaped key `knowledge/`. Pinned by `slugify` tests in `vault-scan.test.ts`; never drop the `|| 'untitled'` fallback
- `journal` entries are auto-appended on `store_memory` only (personal memories only — org stores are skipped); `update_memory` and `delete_memory` do NOT write journal entries; never store to `journal` manually
- `since`/`before` date filters in `recall_memory` / `search_index` / `get_timeline` silently exclude memories with a missing `updated` field (by design); `list_memories` has no date filter
- `rebuild_index` preserves `accessCount`/`lastAccessed` — safe to run anytime
- `vectorStore` native-binding self-heal (`src/vectorStore.ts` `getDb` catch) — each plugin-cache version dir (`~/.claude/plugins/cache/.../<VERSION>/`) ships its OWN `node_modules/better-sqlite3` as **source** (binding.gyp + deps/ + src/, no `prebuilds/`); its install script `prebuild-install || node-gyp rebuild --release` must run to produce `build/Release/better_sqlite3.node`. `install.sh` runs that on first install, but `claude plugin update` creates a fresh version dir and does NOT re-run `install.sh`, so the dir can land source-only and `new Database()` throws "Could not locate binding file". On the FIRST such load failure, `getDb` runs one in-process `npm rebuild better-sqlite3` (resolved via `process.execPath <npm-cli.js>`, no PATH/shell dependency) and retries the import once; the latch `rebuildAttempted` (module-level, once per process) ensures a persistent failure blocks one timeout (180s), not every recall. sqlite-vec is pure JS — only better-sqlite3 needs this. **CRITICAL**: `npm rebuild better-sqlite3` can exit 0 ("rebuilt dependencies successfully") WITHOUT producing the binding — its install script's `prebuild-install` fails offline (`ECONNREFUSED` to the GitHub releases host) and the `node-gyp` fallback is often not installed, so source-compile can't run; npm treats the failed install script as non-fatal and still exits 0. The load RETRY is the ground truth — never claim the rebuild succeeded from npm's exit code alone, and never revert the error message to "rebuild succeeded but reload still failed" (misleading); the recorded error must say the binding is "still missing / not restored" and point at `npm rebuild better-sqlite3` as the manual fix. When no `node_modules/better-sqlite3` is found under the plugin root (`r.attempted === false`), the degrade stays silent (preserves the pre-self-heal optional-dep-absent behavior pinned by `vectorStore.test.ts`). Test seams `__testsSetRebuildImpl` / `__testsGetDb` (NODE_ENV=test guarded, mirror `__testsSetEmbedder`) let the 5 `vectorStore-selfheal.test.ts` cases exercise retry / latch / honest-failure / silent-degrade without spawning real npm; `errors` is imported dynamically per test (after `vi.resetModules`) so it is the same fresh `state.js` instance vectorStore records into. Pinned by `vectorStore-selfheal.test.ts`
- `store_memory` `force=true` — overwrites an existing memory at the same key, preserving `created` and `accessCount`; without it, a duplicate key throws. Refused if the existing memory is tagged `no-prune` (immortal) — even with `force=true` — because a routine re-store could silently strip the tag and quietly make the memory mortal again. The overwrite is a Graphiti-style **supersede, not a drop** (Tech Radar vol.34 #45): the prior body is archived to `<vault>/.superseded/<category>/<slug>.<ts>.md` (excluded from indexing via `EXCLUDED_DIRS`, so it never surfaces in search/recall/list), and the supersession moment is appended to the new frontmatter's `supersededAt[]` chain. "what did I believe and when" is recoverable: the archived filename embeds the same ISO timestamp (colon-stripped for Windows/Git-Bash) as the `supersededAt` entry, so the prior body is locatable from the chain. The archive write is best-effort (a failure does not block the overwrite; the in-band marker still records the supersession). `indexFile` and `coerceMemEntry` carry `supersededAt` into the in-memory meta so it survives reconcile/boot; a corrupt non-array value is coerced to a string array. A full bi-temporal validity-window + relation/graph layer is a later assess-level experiment, not this change
- `no-prune` tag (immortality) — a memory carrying the `no-prune` tag (constant `NO_PRUNE_TAG` in `src/paths.ts`) is (a) excluded from `prune_memories` candidates *before* the retention filter, so it never counts toward `limit` either, (b) refused by `delete_memory` unless `force=true` is passed (mirrors `store_memory`'s `force` pattern), and (c) refused by `store_memory` even with `force=true` — the third removal path, closed so a content re-store can't silently rewrite an ADR's body or strip the tag. Use it for decisions that must not decay out of the prune list or be removed by mistake (e.g. an ADR). Tag-only by design: the `decisions` category is NOT auto-protected — not every decision is immortal, immortality is an explicit per-memory opt-in. The guards are orthogonal to authorship, so they block even the org author; `delete_memory` `force=true` still allows a deliberate teardown (then a fresh store). Amend-in-place uses `update_memory` (it does NOT strip tags). Pinned by `pruneMemories` no-prune exclusion tests in `query.test.ts` and the `delete_memory` force-guard + `store_memory` no-prune guard tests in `index.test.ts`
- Org memory author protection — both `store_memory` (even with `force=true`) and `update_memory` throw if the existing org memory's `author` field differs from the current OS user; personal memories have no author guard
- `personal` + `org` tags are mutually exclusive — `store_memory` throws if both are present on the same memory
- `update_memory` treats a caller-supplied SCALAR `tags` arg (non-array) as lenient: it ignores the field and keeps the existing tags, NOT wipes them to `[]`. The MCP schema declares `tags` as `array`, so a well-behaved client never sends a scalar, but a direct/malformed caller can — and the pre-fix `Array.isArray(tags ?? parsed.data.tags) ? ... : []` wiped the whole field on a scalar (silent data loss on an update that meant to leave tags alone, e.g. only changing `content`). A proper array still replaces; `undefined` (arg omitted) keeps existing. Pinned by T3 regression tests in `index.test.ts` (scalar-keep / array-replace / undefined-keep). The lenient coercion is RETAINED on purpose (6.1-6.3): `McpServer.registerTool` now runs `Zod.safeParse` on the caller's args BEFORE the handler, so a scalar `tags` is rejected at the MCP dispatch boundary with a parse-error CallToolResult and the lenient branch is UNREACHABLE via MCP — but the handler is also called directly by `import_memories`' round-trip and by unit tests, neither of which routes through the Zod boundary, so the coercion is still the sole guard for that internal path. Pinned over stdio by `boundary-enforcement.integration.test.ts` (6.2: scalar tags / wrong-type limit / scalar keys → `isError: true` + `"Input validation error"`; negative numeric `limit` is NOT rejected — the Zod shape has no `.min(0)` and the handler clamps, matching the hand-written schema).
- 6.1-6.3 McpServer migration + schema parity: server.ts uses the high-level `McpServer` + `registerTool` (not the deprecated `Server` + `setRequestHandler`); each tool's Zod raw shape is co-located with its handler in `tools/*.ts` and wired via a per-module `register(server)`; `tools/registry.ts` `wrapHandler` owns the CallToolResult envelope + perf/error instrumentation. The Zod→JSON-Schema rendering the SDK emits for `tools/list` is parity-preserved vs the pre-migration hand-written schema: across all 17 tools the ONLY diffs are two cosmetic, semantically-equivalent quirks — (a) a `$schema: "http://json-schema.org/draft-07/schema#"` meta-key added by `toJsonSchemaCompat` (no validation effect), and (b) `import_memories.memories.items: {}` (Zod's `z.array(z.unknown())`); the hand-written schema omitted `items`, which also means "any item allowed". No `additionalProperties:false` was added, no `default`/`minimum`/`maximum`/`required` shifted. Pinned by `schema-parity.integration.test.ts`, which normalizes those two quirks and asserts exact equality for all 17 tools + an explicit "no `additionalProperties` anywhere" guard — so any future real regression (a dropped default, a shifted min/max, a rejecting `additionalProperties:false`) fails the test. Never relax that normalizer to mask a third diff without documenting its semantic equivalence.
- `sessions` history in `update_memory` — deduplicated, capped at the last 50 entries; not replaced wholesale
- `contentCache` is an LRU (100 entries, 30-min TTL) — `recall_memory(full=true)` and `get_memories_by_keys` read through it; `update_memory` and `delete_memory` invalidate entries on write
- Build externalizes `@huggingface/transformers`, `sqlite-vec`, `better-sqlite3`, and `fsevents` — these must remain optional
- `category` is path-containment-checked — `store_memory` resolves `<vault>/<category>` and rejects values (e.g. `../../../tmp`) that escape the vault root; never trust `category` as a raw path
- `store_memory` rejects a personal (no `org` tag) memory whose `category` is `org` OR any `org/`-prefixed value (e.g. `org/architecture`). The `org/` key prefix is reserved for the org vault, and `reconcileIndex` skips the personal-vault `org/` subtree (so a personal `org/` dir is never mistaken for the org vault) — a personal write landing there is silently orphaned (written, never indexed, invisible to every search/recall/list tool). The guard must catch the *prefix*, not just the exact string `=== 'org'`; a bare `===` guard let `category: 'org/something'` through, writing under `personal-vault/org/...` and losing the memory. Route org memories via the `org` tag, never a reserved `org/` category. Pinned by regression tests in `index.test.ts` (exact + prefix forms, asserting nothing is written to disk).
- Org-author guard **ignores** the caller-supplied `author` for org memories — `effectiveAuthor` is always `os.userInfo().username` for org writes, so `author:'someone-else'` + `force:true` cannot overwrite another author's org memory
- Frontmatter values reject embedded newlines — `frontmatter.ts` throws if a scalar value (`serializeString`) OR an inline-array item (`serializeArrayItem`, e.g. a `tags` element) contains `\r` or `\n`, preventing injection of a new frontmatter key from a value. Both arms (scalar + array-item) are pinned by `frontmatter.test.ts` (the array-item arm is the T4 regression — a `\n` in `tags: [a\nb]` would terminate the frontmatter line and inject the following text as a new key on re-parse)
- `withExecutiveSummary` (frontmatter.ts) is idempotent — re-applying to content that already begins with `## Executive Summary` (after `trimStart()`) does NOT prepend a second copy. Without the trimStart check, a caller that normalizes user-supplied content via `withExecutiveSummary` (e.g. `update_memory` on a body that already shipped) would double the header on every edit, growing the file. The first-time path (no header yet) prepends; the re-apply path is a no-op. Pinned by T5 tests in `frontmatter.test.ts` (header-present + leading-whitespace cases, asserting exactly one `## Executive Summary`).
- `privacy-filter.ts` `safeStringify` catches circular refs / BigInt and returns `''` so the filter can never crash-open on a hand-edited teammate-pushed frontmatter value. A thrown `JSON.stringify` would let a secret-laden file sail past the filter by crashing it; the fallback is conservative (the named-field text in `text` still scans title/author/tags/sessions and the body, so a secret in a named field OR body is still caught). Pinned by T6 tests in `sync-org-memory.test.ts` (circular `data.self = data` does not throw; named-field email in a circular object is still blocked).
- T2: `store_memory` rejects `category: 'org'` AND `category: 'org/something'` (the prefix form) for a personal memory — both arms pinned by `index.test.ts` "Reserved Org Cat" (exact) and "Prefix Org Cat" (prefix) tests, which assert the throw AND no stray file under `personal-vault/org/`. The pre-fix exact-only `===` guard let `category: 'org/architecture'` through, writing under `personal-vault/org/architecture/foo.md` and orphaning the file (reconcileIndex skips the personal `org/` subtree).
- Index files (`index.json`, `invertedIndex.json`, `.index-cache.txt`) are written atomically via write-`.tmp` + `rename` — `persistence.ts` `atomicWrite()`; never write these files directly with a plain `writeFileSync`
- `flushPending` (the SIGTERM/SIGINT/beforeExit flush) gates the O(N) `recalcIdfNow` on `dirtyTokens || idfTimer !== null` — a pure read-only exit (only a `scheduleAccessSave` access-bump pending, zero token changes) runs `saveNow` to persist the access bump but SKIPS the inverted-index rebuild, since the inverted index already reflects `memIndex`'s tokens. The once-per-session rebuild backstop is preserved only when tokens changed or a recalc was already queued; never make `flushPending` unconditionally call `recalcIdfNow` again, or every read-only session pays a full `rebuildInvertedIndex` + `invertedIndex.json` write on shutdown.
- `index.json` has a **single-writer assumption** — no `flock`/CAS. Each Claude Code window spawns its own total-recall process; concurrent sessions both flush via `atomicWrite` and last rename wins. Disk-durable fields (`title`/`tags`/`content`/`sessions`) are re-derived from `.md` files on boot, so a clobber loses no memory content — only the runtime-only `accessCount`/`lastAccessed` (soft Ebbinghaus signals) can be reset. Don't run multiple heavy-write sessions in parallel if retention-decay accuracy matters
- SessionStart hooks emit `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":…}}` — omitting `hookEventName` silently drops the context (the plugin's core feature); JSON-encoding uses `node`, not `python3`
- 8.5: the two SessionStart hook manifests use a **per-client timeout field name** — `hooks.json` (Claude Code) and `hooks.gemini.json` (Gemini CLI) both use `timeout` (ms). The field name is dictated by each client's hook schema, not a typo — do NOT "normalize" them away from what the client expects. When adding a new SessionStart/SessionEnd/PreCompact hook, mirror the existing per-manifest field for that client. The two manifests (`hooks/hooks.json`, `hooks/hooks.gemini.json`) are the ONLY hook sources — install.sh no longer embeds an inline copy (the `--standalone` path was removed).
- Frontmatter keys are escaped (`escapeRegExp`) before being interpolated into a RegExp in `frontmatter.ts` — a key is any `[^:\s]+` literal (incl. metacharacters; a teammate can push one via the shared org vault), so it must match literally; never interpolate a parsed key into `new RegExp` raw, or a key like `(a+)+` is mis-matched and an explicit `(a+)+: []` array is wrongly dropped
- The org `index.json` is the source of truth that `scripts/sync-org-memory.mjs` commits to the shared org-sync branch (`config.orgBranch`, default `org-vault`), so a corrupt parse must NOT be catch-wiped: `loadOrgIndex` throws when the file exists but is unparseable/non-object (interrupted `atomicWrite`, bad manual edit, merge-conflict marker) and the throw propagates to `main().catch` (logged to `~/.total-recall/org/.sync-errors.log`, exit 0), leaving the file untouched for manual recovery. Cold start (no `index.json` yet) returns `{}` — the first sync must be allowed to create it. The personal `index.json` is self-healing (rebuilt from `.md` files on boot); the org one is not.
- `reconcileIndex`'s walk catches `readdirSync` per directory. ENOENT (a dir gone since the walk scheduled it) skips silently, but a NON-ENOENT error (EACCES on a chmod'd subdir, EMFILE on fd exhaustion) is recorded via `recordError` (`reconcile readdirSync(<dir>): …`) so the subtree that just "vanished" from search is observable in `get_stats.recentErrors` instead of silently pruned — never wrap that readdirSync in a bare `catch { return; }` again, or an unreadable vault subdir becomes invisible with no signal.
- Git tests must not depend on the developer's `~/.gitconfig` — `sync-org-memory.e2e.test.ts` operates directly inside a local **bare** repo fixture (`remote.git`, its stand-in for a server-side remote), and a user-global `safe.bareRepository=explicit` (a common hardening setting against embedded-bare-repo attacks) makes every git command run with cwd inside it fail (`fatal: cannot use bare repository`). The suite therefore injects `safe.bareRepository=all` via git's env-config mechanism (`GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=safe.bareRepository`, `GIT_CONFIG_VALUE_0=all` in the test's `GIT_ENV`), which applies ONLY to processes the test spawns — the developer's global config and protection stay untouched. If you add another test that shells out to git against a bare fixture, reuse `GIT_ENV` (or the same env-config trio); never "fix" this class of failure by editing the user's global git config.
- `loadMemIndex` (`persistence.ts`) reads the personal `index.json` at boot with a try/catch. ENOENT is the expected cold start (no index.json yet — the first store creates it) and stays silent, but a NON-ENOENT failure (corrupt JSON from an interrupted `atomicWrite`, a bad manual edit, EACCES) is recorded via `recordError` (`loadMemIndex parse failed (rebuilding from .md files): …`). The personal index is self-healing (`reconcileIndex` rebuilds from the `.md` files), so it isn't data loss — but the silent discard would hide a real condition and the loss of the runtime-only `accessCount`/`lastAccessed` fields. Never collapse that catch back to a bare `catch { return; }`, or a corrupt index.json becomes invisible. (Distinct from the org-index guard in `sync-org-memory.mjs`, which THROWS on a corrupt committed index that propagates via git; this is local-only and benign.) Pinned by regression tests in `persistence-loadmemindex-error.test.ts` (parse + EACCES record, ENOENT silent).
- `shutdown()` (src/index.ts) is **idempotent via a module-level `shuttingDown` latch** (6.10) — the four exit triggers (`SIGTERM`, `SIGINT`, stdin `end`, stdin `close`) can fire concurrently (e.g. SIGTERM arrives while stdin is also closing, or a double signal); without the latch, `flushEmbeddings()`'s awaited drain and `process.exit(0)` could run twice and race. The latch is set at the top of `shutdown()` and the second-and-later calls return immediately. `flushPending()` (sync index write) runs first, then `await flushEmbeddings()` drains in-flight embed→upsert, then `process.exit(0)`. Never remove the latch or move `process.exit` outside the single-flight path, or a concurrent signal can exit before the flush completes. Pinned structurally by `index-stdin-end.test.ts` (asserts the `shuttingDown` guard exists in source) and dynamically by `src/__tests__/integration/shutdown-sigterm.integration.test.ts` (11.2: spawns real `dist/index.js`, stores a memory, SIGTERMs before the 1s `scheduleSave` debounce fires, and asserts the stored key lands in `index.json` on disk before exit — proving `flushPending` ran on SIGTERM; a second test fires SIGTERM+SIGINT in rapid succession and asserts clean exit 0 + index.json intact, pinning the latch's runtime contract).
- `store_memory` inputSchema declares `key`/`created`/`updated`/`sessions` (6.5) — the handler in `store.ts` already accepted these (the `import_memories` round-trip passes them to preserve the original key location and timestamps), but the schema omitted them, so a client had no way to pass them explicitly and they were undocumented. They are NOT required: a normal store derives the key from `title`/`category` and stamps `created`/`updated` from now; `sessions` is seeded from `sessionId`. Declaring them documents the restore path; do NOT make them required, or a normal `store_memory` call breaks.
- `rerank_memories` `keys` is capped at **200** (6.6) — the schema declares `maxItems: 200` and `rerank.ts`'s `MAX_KEYS=200` slices extras off the front (preserving original order) before the embed/score loop. The schema `description` notes the cap. An unbounded schema let a client pass thousands of keys, each costing an embed; never drop the `maxItems` or the `slice(0, MAX_KEYS)` guard.
- `delete_memories` `confirm` has **no default** (6.7) — it is `required` AND must be explicitly `true`. The schema previously declared `default: false` alongside the `required`, a contradiction (a required field has no default). The dead `default: false` was dropped; the handler still rejects `confirm !== true`. Never re-add a default to a required field.
- `export_memories` returns `{count, memories, errors}` (6.8) — an unreadable memory body (file deleted between list and read, EACCES, corrupt frontmatter) is NOT silently exported as `content: ''` (which `import_memories force=true` would then overwrite real content with). Instead the entry is `{key, error: 'unreadable or missing memory file'}` and counted in `errors`; `import_memories` skips any entry carrying an `error` field so the round-trip can't clobber a live memory with an empty body. Never collapse the error entry back to a bare `''` export, or a failed read becomes a destructive import.
- `delete_memories` records a reserved key as a **per-key error, not a batch reject** (6.9) — the up-front `keys.some(isReservedKey)` throw was dropped. Now the per-key loop's `deleteMemory` catch records a reserved (`no-prune` without `force`) key in `errors` like every other per-key failure, and the rest of the batch proceeds (deleted count reflects only the keys actually removed). A single reserved key no longer aborts the whole batch. The `isReservedKey` import was removed from `bulk.ts` (no longer used); do NOT re-add the up-front throw. Pinned by `bulk.test.ts` (6.9) and `reserved-keys.test.ts` (updated from the old batch-reject contract to the new per-key contract).
- Personal-vault durability (H1, v1.1.12) — the personal vault has a **single-writer, self-healing index** but its `.md` files are the ONLY copy of memory content (unlike the org vault, which is git-backed by design). The 2026-07-31 incident showed the failure mode: when the `.md` files were cleared out-of-band, the self-healing index (rebuilt FROM those files) had nothing to heal from, and recovery required mining session transcripts. Mitigation: `~/.total-recall/personal-vault/` is a **local-only git repo** (one-time `git init`, never a remote — it holds private memories; a `pre-push` hook hard-blocks pushes as belt-and-suspenders), and `session-end.sh` auto-commits it each session (best-effort, silent on failure). The hook **only commits an existing repo** — it does NOT `git init` (so a user who deliberately un-inited stays that way) and never touches a remote. `.superseded/` and `*.tmp.*` are gitignored. Pinned by the two H1 cases in `hook-scripts.test.ts` (auto-commit-when-repo / no-init-when-not-a-repo, asserting no remote is created). A future loss is now a `git -C ~/.total-recall/personal-vault restore` away.
- SessionEnd envelope shape (v1.1.10) — `session-end.sh` emits `{"continue":true}`, NOT `{"hookSpecificOutput":{"hookEventName":"SessionEnd","additionalContext":…}}`. The SessionEnd hook event REJECTS the additionalContext shape ("Hook JSON output validation failed — (root): Invalid input") because there is no ongoing conversation to inject context into at teardown — it worked for SessionStart, so the original author mirrored it and it failed 92× silently. The hook's real work is side effects (log + SIGTERM flush + H1 auto-commit), never stdout. Pinned by `hook-scripts.test.ts` (asserts `continue:true` + `hookSpecificOutput` undefined). Never re-add additionalContext to a SessionEnd envelope.
- Org working-tree wipe tripwire (H2, v1.1.11) — `sync-org-memory.mjs` `guardTreeWipe()` wraps the only tree-mutating git op (`git switch BRANCH`): it snapshots HEAD `.md` count + disk `.md` count before, and if the op collapses a non-empty tree to zero while HEAD still has files, it restores the tree from HEAD (`git restore --source=HEAD`, `checkout HEAD --` fallback) and throws rather than committing an empty tree. This does not "fix" the (unreproducible) wipe cause — it makes the EFFECT non-silent and self-recovering. The module has a main-guard (`import.meta` vs `argv[1]`) so it is test-importable without auto-running a sync; the helpers are exported. Pinned by `sync-org-wipe-guard.test.ts`. Related: the `loadtest.ts` real-HOME guard (refuses to run against the real HOME unless `LT_ALLOW_REAL_HOME=1`) — also committed in v1.1.11.
