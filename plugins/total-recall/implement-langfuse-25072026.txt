================================================================================
THE STRUCTURAL MISMATCH
================================================================================

Langfuse covers 70% of LLM-observability concerns that don't exist in this plugin:

  Langfuse capability       | Maps to total-recall         | Relevance
  ───────────────────────── | ──────────────────────────── | ──────────
  Generations + prompts     | *nothing* (no LLM calls)      | n/a
  Token usage / cost        | *nothing* (no LLM calls)      | n/a
  Prompt management         | *nothing* (no prompts)        | n/a
  Spans over function calls | one MCP tool call            | low → get_stats already has p50/p95/p99
  Datasets + versioning     | adversarial query set         | **high** if recurring eval work
  Experiments + scoring     | recall@5, MRR, NDCG@5       | **high** if recurring eval work
  Traces (observability)    | last 10 errors + perf hist   | low → already in state.ts

Embeddings are in-process HuggingFace; the only genuine LLM boundary
(PreCompact learning extraction) is executed by Claude Code, not by the server.
The plugin only receives JSON lines in hooks/scripts/store-learning.mjs.

================================================================================
OPTION A: OFFLINE EVAL BACKEND (RECOMMENDED)
================================================================================

Scope
  • Zero changes to shipped plugin
  • New file: scripts/eval/langfuse-experiment.mjs
  • New dev dependencies: @langfuse/client, @langfuse/tracing, @langfuse/otel,
    @opentelemetry/sdk-node

Implementation
  • Spawn dist/index.js over stdio (exactly as recall_harness.py does)
  • Use Langfuse's experiment runner to loop queries through the MCP tool surface
  • Reuse ranking metrics from recall_harness.py (NDCG@5, recall@5, MRR)
  • Create a persistent dataset on Langfuse Cloud or self-hosted instance

Code skeleton
  ────────────────────────────────────────────────────────────────────────────
  import { NodeSDK } from "@opentelemetry/sdk-node";
  import { LangfuseSpanProcessor } from "@langfuse/otel";
  import { LangfuseClient } from "@langfuse/client";

  const otel = new NodeSDK({ spanProcessors: [new LangfuseSpanProcessor()] });
  otel.start();
  const langfuse = new LangfuseClient();

  // task = drive the real MCP surface (spawn dist/index.js, JSON-RPC recall_memory)
  const task = async ({ item }) => callTool("recall_memory", {
    query: item.input,
    limit: 5
  });

  const result = await langfuse.experiment.run({
    name: `recall-quality @ v${version} hybrid=${hybrid}`,
    data: goldQueries,                        // or Langfuse-hosted dataset
    task,
    evaluators: [ndcgAt5, recallAt5, mrr],    // reuse metrics code
  });
  console.log(result.format());
  await otel.shutdown();
  ────────────────────────────────────────────────────────────────────────────

Trigger
  • Per release (version bump in pre-commit checklist)
  • Optional: gate CI with langfuse/experiment-action

Outcome
  Turns the Stryker finding ("TF-IDF unit tests are formula-weak, ~half the
  mutants survive") into a trend line across versions instead of a one-shot
  PASS/FAIL. Each run is versioned, comparable, and shareable.

================================================================================
OPTION B: OPT-IN RUNTIME TRACING (ONLY if per-query forensics needed)
================================================================================

Scope
  • New file: src/telemetry.ts (lazy-load wrapper)
  • Modify: src/server.ts (wrap dispatch handler)
  • New dev dependencies: same as Option A
  • New environment variable: LANGFUSE_PUBLIC_KEY (gates tracing on/off)

Implementation
  ────────────────────────────────────────────────────────────────────────────
  // src/telemetry.ts — mirrors lazy-load/degrade pattern from embeddings.ts
  let tracer: any = null, tried = false;
  export async function traced<T>(
    name: string,
    args: any,
    fn: () => Promise<T>
  ): Promise<T> {
    if (!process.env.LANGFUSE_PUBLIC_KEY) return fn();   // off by default
    if (!tried) {
      tried = true;
      try { tracer = await import('@langfuse/tracing'); } catch {}
    }
    if (!tracer) return fn();
    return tracer.startActiveObservation(name, async (span: any) => {
      span.update({ input: redact(args) });             // reuse privacy-filter.ts
      const out = await fn();
      span.update({
        output: {
          count: Array.isArray(out) ? out.length : 1,
          keys: keysOf(out),
          scores: scoresOf(out)
        }
      });
      return out;
    });
  }

  // src/server.ts — at CallToolRequestSchema handler
  const result = await traced(name, args, () => handler(args ?? {}));
  ────────────────────────────────────────────────────────────────────────────

Four non-optional constraints

  1. **stdout is the JSON-RPC channel.** Any OTel diagnostic writes to stdout
     corrupt the MCP protocol and kill the session. Pin OTel logger to stderr
     (only); exporter must be OTLP/HTTP only.

  2. **Bundle size.** esbuild bundles everything except --external entries.
     @opentelemetry/sdk-node would inflate dist/index.js (624K today) for
     *every* consumer. Must be --external + optionalDependencies, like
     @huggingface/transformers.

  3. **Flush on exit is async, shutdown is sync.** index.ts:41 calls flushPending()
     synchronously to ensure index.json is durable. sdk.shutdown() returns a Promise.
     On beforeExit/SIGTERM, the process can exit before the exporter drains, so
     short sessions silently lose spans. Solvable but requires surgery on a
     deliberately-synchronous exit path.

  4. **Privacy inversion.** Query text, memory titles, previews are exactly what
     the fail-closed org privacy filter exists to protect locally. Shipping them
     to Langfuse Cloud contradicts the plugin's design premise. Mitigation:
     self-host Langfuse (docker compose), or trace metadata only (counts/latency/
     scores/hybrid_degraded), never IO.

================================================================================
PROS AND CONS
================================================================================

OPTION A (Offline eval backend)
──────────────────────────────────────────────────────────────────────────────
Pros
  ✓ Retrieval quality gets history and comparison, not a single PASS/FAIL
  ✓ Datasets become a durable asset; adversarial queries accumulate over time
  ✓ OTel-native → no lock-in; same spans can go to SigNoz/Jaeger/self-hosted
  ✓ Makes the hybrid path's silent degradation visible as a rate (not buried
    in recentErrors)
  ✓ Fully reversible; never touches shipped code
  ✓ Works offline with local datasets; optional Langfuse Cloud for sharing

Cons
  ✗ Requires explicit run; doesn't give real-time observability
  ✗ Heavy platform (Langfuse self-hosted = Postgres + ClickHouse + Redis + S3)
    for three metrics (recall@5, MRR, NDCG@5)
  ✗ Duplicates existing tooling (DeepEval-style Python harness)

Score: **RECOMMENDED** if eval becomes recurring (version-to-version TF-IDF tuning)
       **SKIP** if it's one-time (just show current state is good)

──────────────────────────────────────────────────────────────────────────────

OPTION B (Runtime tracing)
──────────────────────────────────────────────────────────────────────────────
Pros
  ✓ Per-query observability; can debug slow/anomalous recalls in real-time
  ✓ Integrates seamlessly into Claude Code sessions
  ✓ Experiments can be run against live production data

Cons
  ✗ **Severe impedance mismatch:** no generations, no tokens, no cost, no prompts.
    Using a heavy LLM-observability platform to store counts/latency is a
    category error.
  ✗ **New supply-chain surface:** adds a third-party SDK to a privacy-first
    local tool; exactly the supply-chain caution the Radar raises under
    Agent Skills (#72)
  ✗ **Network egress + external service:** contradicts the plugin's "local,
    no daemon" value proposition
  ✗ **Duplicates existing observability:** get_stats already exposes:
      • Tool latency percentiles (p50/p95/p99)
      • Bounded error sink (last 10 errors, always observable)
      • Recent perf histogram
  ✗ **Operational burden:** self-hosted Langfuse is a serious footprint next
    to a plugin whose value is "zero dependencies"
  ✗ Four hard constraints (stdout safety, bundle size, async shutdown,
    privacy inversion) make this risky
  ✗ Single-user, single-process: no traffic volume to make aggregate
    dashboards meaningful

Score: **SKIP** unless you need real-time per-query forensics (which you don't yet)

================================================================================
RECOMMENDATION
================================================================================

Do **OPTION A ONLY**, and only if either condition holds:

  (a) You're actively tuning TF-IDF weights, RRF k value, or the embedding
      model, and want to know whether each change improved recall quality.

  (b) You want to build a dataset of adversarial queries over time and
      measure progress across versions.

Otherwise, the single gap Option B would close—"how often does the hybrid
path degrade to TF-IDF?"—is one counter in get_stats away. Don't build an
observability platform for it.

If you do Option A:
  • Self-host Langfuse or use the free cloud tier
  • Store metadata only (dataset + results), no memory bodies
  • Run per release (version bump is your trigger)
  • Treat experiment results as immutable artifacts (version-tagged)
