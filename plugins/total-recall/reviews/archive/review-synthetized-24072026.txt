PHASE 4 — PERSISTENCE / ORG-SYNC DURABILITY
================================================================================
4.1  atomicWrite tmp-write fallback overwrites target non-atomically.
     (review-ollama 1.3 = GLM 4.3 = review-claude C-13, MED) On tmp-write
     failure the catch does a direct writeFileSync(p) — a crash mid-fallback
     corrupts the file atomic-write was meant to protect; and the rename-catch
     fallback (persistence.ts:101-106) is unguarded and can throw at boot.
     FIX: on tmp-write failure, recordError and leave the last-good file
     untouched (don't overwrite); wrap the rename fallback in try/recordError.

4.2  org-sync queue job deleted BEFORE the sync runs.
     (review-ollama 1.4 = 9.2, MED) sync-org-memory.sh:104-108 rm -f "$job"
     then runs sync; a failed push permanently drops the org memory with no
     retry. FIX: rm only AFTER a successful sync; on failure leave/re-enqueue.

4.3  org-sync queue job files are not actually atomic (cross-fs mv).
     (review-claude C-7, MED) JOB_TMP=$(mktemp) defaults to /tmp (often tmpfs);
     mv into $HOME queue is copy+unlink, not atomic — a drain can read a partial
     job. FIX: mktemp on the same filesystem, e.g.
     "$HOME/.total-recall/org/.job.XXXXXXXX", then mv into the queue.

4.4  org-sync push failures exit 0 and are never surfaced.
     (review-ollama 9.3 = GLM 6.3, MED) sync-org-memory.mjs logs to
     .sync-errors.log and exits 0; nothing reads it. FIX: SessionStart hook (or
